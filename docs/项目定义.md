# 项目定义

> 这份文件只干一件事：说清这个项目**是什么、给谁用、做什么、不做什么**。
> 觉得方向飘了、想加新功能之前，先回来读一遍。

---

## 一句话

**一个能看见现场、听懂提问、用语音回答的嵌入式视频终端。**

用在**人不在但是需要知道现场情况**的地方：工位、机柜、仓库、大棚。

---

## 它解决什么问题

传统摄像头只能「录下来事后看」。人不在现场时想看点什么，得走一遍：

掏出手机 → 连内网 → 找通道 → 拉流 → 自己盯画面判断

三个毛病：**要人主动去看、要带宽、要自己判断**。

这个终端把它反过来：**一句话问它，它看一眼再回答**。不用拉流，不用人判断，一帧图几百 KB 的异步请求，带宽占用可以忽略。

---

## 四个功能（全部就这四个）

| # | 功能 | 用户说什么 | 设备做什么 | 状态 |
|---|---|---|---|---|
| 1 | 看见 | — | V4L2 采集、MJPEG 推流、屏幕预览 | ✅ v1.0 |
| 2 | 听见 | 随便说话 | ALSA 录音，检测到人声落盘 | ✅ 第 4 步 |
| 3 | 听懂并照做 | "拍一张" | 抓当前帧存文件，回"已拍一张" | ✅ 已验证 |
| 4 | 看懂并回答 | "这是什么" | 抓帧 + ASR + 视觉模型，回答并念出来 | ✅ 已验证（念出来待耳机） |

**功能 3 和 4 才是这个项目的价值**，1 和 2 是地基。

---

## 明确不做

| 不做 | 为什么 |
|---|---|
| 日常闲聊 | 套个 API 谁都会，跟"看见现场"无关。只答和本设备能看到的东西有关的问题 |
| 多轮对话、上下文记忆 | 一问一答就够，记忆只会引入状态管理的复杂度 |
| 本地模型推理 | A55 四核算力不够。**端侧只做数据通路，重计算上云** |
| H.264 硬编码 | MPP 要重写数据流第一层，四周换不来对应加分 |
| RTSP | MJPEG 已经把协议这块讲透，加 RTSP 是稀释 |
| 安卓 App / Qt 界面 | 和嵌入式 Linux 主线不搭，已有 Web 页面够用 |

## 三分钟演示脚本

```
1. 浏览器打开 http://<板子IP>:8080    实时画面，证明在采在推
2. 指着屏幕说"拍一张"                 串口打印已存 shot_<帧号>.jpg
3. 说"桌上有什么"                     3~8 秒后念出答案
4. 打开 /status                      {"fps":15.0,"drop_stream":0,...}
5. 拔掉摄像头再插回                   自动重连，画面恢复
```

**第 3 步是重点**，第 5 步是加分——证明不是跑一次就死的演示。

## 简历一句话

> RK3568 多模态视频终端：V4L2 采集 + 三线程解耦 + mmap 环形缓冲，HTTP MJPEG 推流与 framebuffer 本地预览，异常自恢复；扩展 ALSA 音频链路，接入云端 ASR 与多模态模型，实现"语音提问、即时抓帧、看图回答"的闭环，端侧只做数据通路，重计算全部上云。

## 判断新功能该不该加的三条

1. **它是不是"看见现场"的一部分？** 不是就不加。
2. **它能不能用一句话演示出来？** 不能就不加。
3. **它会不会削弱"端侧只做数据通路"这个定位？** 会就不加。

三条都过，再谈工作量。
